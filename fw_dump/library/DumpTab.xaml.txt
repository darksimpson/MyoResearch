    <sys:String x:Key="DumpTip">A Fletcher16 over two bytes determines both of them modulo 255, so every request yields two bytes. Modulo 255 the values 0x00 and 0xFF are identical, and that is the one thing this cannot tell apart. Three things settle such bytes: the Scan command proves 8-byte blocks erased, so whole erased areas come out exactly; below 0xF000 an update mirrors flash into the spare bank, where offering the armband a write makes it compare rather than program, which settles the byte exactly (this covers the factory calibration, the user settings, the bootloader and classifier slot 0); and anywhere else a reference image can be consulted. Whatever is left is listed by address in the report, with 0x00 assumed. An application dump is also loaded back through the same validator the bootloader uses, so it either proves itself safe to flash or says why not.</sys:String>
    <sys:String x:Key="DumpReferenceTip">Only consulted for bytes the armband cannot pin down as 0x00 or 0xFF, and only at addresses the file actually defines. Bytes the armband did report are always kept, and the report counts how many of them differ from the reference, so a stock image can be used to resolve a patched build without hiding the patch.</sys:String>
